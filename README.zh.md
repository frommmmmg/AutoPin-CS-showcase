> **本仓库仅用于展示，不公开源码。** AutoPin-CS 不开源，所以这里没有代码，只介绍它做什么、怎么构建、长什么样。想聊聊它，请通过我的 [GitHub 主页](https://github.com/frommmmmg)联系我。

**面向大规模社交媒体内容运营的调度与客户端集群管理系统。** 中心服务器向一队 Windows 客户端派发任务，再加一层 AI Agent，让运维人员用日常语言就能操作整个系统。

运行一大批无人值守的桌面客户端，本质上是个运维问题。怎么在不把整队机器搞挂的前提下发布新版本？怎么让每台新机器都用同一种方式上线？怎么找出那台悄悄出问题的机器？AutoPin-CS 就是围绕这些问题建起来的系统，它的大部分代码都在做一件事：让答案可重复、可检查、可恢复。

### 它能做什么

**服务端**
- **集中调度与管理。** Flask/uWSGI 服务加 MySQL，管理任务、订单、客户端登记、任务日志与结果、备份和统计分析。
- **契约与表结构纪律。** 每张表的结构都有版本，并归属于一个模块；就绪检查会让调度器等到数据库处于预期状态才启动。

**客户端集群**
- **由 Python 守护进程组成，有多种运行模式**，运行浏览器自动化流程：长驻 worker、由服务端下发的单任务模式，以及其他任务类型。
- **能穿透 Windows 会话隔离的桌面代理。** 它可以看到并操作真实的用户桌面，所以远程诊断有截图和进程控制，而不是对着日志猜。
- **视频预处理。** 一套经过验证的批处理流程，把视频规范化成保守的 H.264/AAC 参数，连老旧的 Windows 和浏览器组合也能接受。

**发布工程**
- **从不放宽的发布门禁。** 每次客户端升级都先构建完整包、登记为未激活、**在真实的金丝雀机器上验证**，然后才激活，并随时可回滚。构建成功、压缩包能解开、收到一次心跳，都不算升级成功。

**AI Agent 层**
- **把运维写成 Agent 技能。** 新机器上线、远程客户端诊断、调度器巡检、异常账号的分诊、发版，都写成 AI Agent 可以执行的技能。每个技能是一串固定步骤，带验证门禁和证据读回，由运维人员的一句话触发。

## 工程笔记

- **决策都写下来了，而且很多。** 400 多份架构决策记录说明了事情为什么是现在这样，其中不少是关于给数据库表结构编版本、定归属，让启动和迁移保持可预期。
- **每个 bug 都有复盘和同类排查。** 约 290 份 bug 记录，每份都写明根因、回归测试，以及在别处查找同类缺陷的结果。做完这一步，bug 才算关闭。
- **要证据，不要侥幸。** 只有拿到真机证据，发布才算成功：进程树稳定、桌面会话正常、成功状态已持久化、没有更新的失败或回滚。包的检查包括成员清单、ZIP 校验、长度、SHA-256，以及与机群里最老解释器的兼容性。
- **恢复路径在需要之前就设计好了。** 回滚路径、金丝雀机器的已验证恢复通道、完整安装器恢复手册都有书面记录，原始的失败日志会被保留，而不是被覆盖。
- **密钥不进代码，也不进命令行。** 凭据放在操作系统的钥匙串里，工具用到时才交给它。
- **Agent 守的规矩和人一样。** Agent 技能和代码一起受版本控制，带着同样的安全规则（不许跳过金丝雀、不许凭猜测判断日志来自哪个入口），并且必须以确认改动已推送作为收尾。
